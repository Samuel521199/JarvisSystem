<a id="observability"></a>
## 可观测性、资源与运维



<a id="observability-1"></a>
### 用户应能看到的内容

当前正在做什么、哪些任务等待、下一步是什么。
- 每个节点的在线、自治、同步中、隔离或降级状态。
- 哪个模型或工具处理了任务、成本和预算剩余。
- 当前人格、技能、模块和运行版本。
- 最近一次进化改了什么、效果如何、能否恢复。
- 记忆来源、同步范围和待解决冲突。
- 外部动作是已确认、失败，还是结果不确定。

呈现关键状态和证据摘要，不要求展示内部模型推理全文。

<a id="module-monitoring"></a>
### 设置中的模块观察与维护（0.1.30）

**已实现子集。** 工作台“设置 → 模块与升级”显示本实例 22 项观察条目（含原生技能、本地精确计算、快速 ZipVoice 与 CosyVoice3）；卡片分开表示安装、启用、活动、健康、版本、近期使用和升级方式，不把“文件存在”“服务在线”或“已经写在设计中”混为可用能力。具体接口归[模块观察契约](contracts.md#module-monitor-contract)；0.1.30 增加自然语言目录报告观察，验证见[本轮记录](delivery-validation.md#sample-task-evidence)，0.1.28 记忆覆盖修复和原升级通道分别见[0.1.28](delivery-validation.md#runtime-entry-evidence)、[0.1.22](delivery-validation.md#module-monitor-evidence)。

**0.1.28 修复了此前记忆占位过时的问题。** 明确事实、项目资料和扩展登记数据库尚未创建时显示“首次使用时创建”，不会因为打开监控而新建或迁移数据库；损坏、版本不兼容或读取超时只让对应条目显示“观察失败”。读取采用只读连接、50ms 锁等待及约 150ms SQLite 指令预算；这不是底层磁盘 I/O 的硬时限或全库完整性验证。

有效记录数量不等于调用次数，单独显示“有效事实/资料/登记”和最近观察记录的修改时间；尚无调用计数的模块明确标注。资料记录存在不证明每份源文件可访问，MCP 登记库可读不证明远端服务器在线。完整自动记忆提取和扩展执行仍未实现。展开页面下方“初始知识与能力清单”可按文字筛选种子知识、规则、能力及技能；语义归[种子运行入口](knowledge-learning.md#seed-runtime-entry)。

数据库使用次数是对应来源**最近最多 1,000 条记录**内的计数；本地计算采用上表的本次启动计数。不同模块来源不同，不能相加成统一业务量，也不能以零次断言从未使用。模块故障显示“观察失败”或“不可用”；最后一次观察时间、缓存过期和采集中状态始终可见。提供全部、正在使用、待命/近期未使用、需要关注、尚未实现筛选。

监控仅在页面可见时请求，正常约 8 秒；离开类别或浏览器页签隐藏后停止轮询。后端所有页面共享缓存和单个采集线程，刷新冷却 2 秒、正常缓存 8 秒，数据库为限时只读、每次有记录上限；固定本机探针 0.8 秒超时，不加载权重、不自动拉起模型或浏览器。一个采集器失败不取消其他采集器。首次或后台维护进行中只加快读取缓存，不提高实际采集频率。

升级复用[现有运行版本协议](evolution-release.md#service-continuity-4)：填写可信本机 ZIP → 导入候选 → 验证候选 → 选择下次启动版本；可以恢复上次选择。只有显式操作才会导入或执行验证；校验摘要不证明包来源，候选验证会运行包内代码。独立维护通道一次一项，不占聊天名额或任务队列，不覆盖正在运行的源码或终止服务；候选失败保留当前服务。最后 20 项维护回执落在业务目录的独立小文件；进程退出时未完成的回执恢复为 UNKNOWN，不自动重放。关闭设置页面不会取消已经受理的维护。

本地模型启停复用同一条维护通道；加载/停止会改变该可选组件状态，原升级操作仍只准备后续运行包。具体所有权、内存准入和失败处理以[本地运行语义](models-offline.md#local-model-runtime)为准，入口见[本地模型使用方法](core-bootstrap.md#offline-task-entry)。

**连续运行边界。** 当前是准备升级与对话通道分离，并未实现同包各模块任意热替换。受管槽位正在使用时，既有版本锁可能拒绝维护，页面显示失败；源码运行可准备下次版本，仍须结束当前实例后显式从运行包启动器启动。没有从网页直接重启的按钮，不冒险中断现有对话。单线程维护仍消耗磁盘/CPU，资源饱和时的时延上界、逐模块 CPU/GPU/内存归属、无损任务迁移和所有模块独立热升级尚未验证；不能宣称绝对零性能影响。

<a id="ui-asset-degradation"></a>
### 界面资源与聊天核心的故障隔离（0.1.38）

启动时由独立 [UIAssets](../apps/web/ui_assets.py) 装载本机固定清单，不从请求路径读取文件。聊天基础页、主题与工作区样式、附件适配、会话归档和会话工作区脚本属于基础依赖；缺失或空文件仍明确阻止启动，不能以一个无法保存或发送的页面冒充就绪。它们的唯一代码清单为 `CORE_ASSETS`。

其余已登记界面资产缺失、为空或无法读取时仅记为降级：聊天页显示简短提示与可展开文件名，缺失脚本不再加载，直接请求该资产返回 503。设置入口的主页面/脚本不可用、品牌预览资源不完整时，返回带“返回聊天”的降级页；不偷偷下载资源、不修改安装文件、不触发模型。核心是否就绪仍单独判断，观察字段见[状态接口](contracts.md#recovery-contract)。

这只是启动时的界面资产隔离，不是任意 Python 模块导入、数据库和全部运行依赖的隔离，也不代表热更新。资源修复后需重启才重新读取。运行包摘要和完整性验证仍严格执行；本机宽容降级不能作为发布缺失文件的理由。验证见[基础修复复验](delivery-validation.md#foundation-repair-evidence)。

<a id="machine-resource-usage"></a>
### 设置总览中的整机资源（2026-10-16 增量）

本增量 implemented/verified 范围为 Windows 本机源码部署：设置总览顶部展示紧凑的 CPU、GPU、内存、显存四格。统计范围是**整台电脑**，包含其他程序；不代表 Jarvis 单进程消耗。数据来自本机系统接口，不调用模型、不上传硬件统计，不形成持久历史。

- CPU：Windows PDH `Processor Information(_Total)` 的处理器时间比例；计数器不可用且逻辑处理器不超过 64 时回退 `GetSystemTimes` 时间差。数值随采样窗口变化，不承诺与任务管理器的频率加权数值一致。
- 内存：`GlobalMemoryStatusEx` 的物理总量减可用量，显示比例与已用/总量，单位 GiB。
- GPU：PDH `GPU Engine` 按同一物理引擎合并进程占用，再取最忙引擎；多卡取最忙值，不把不同引擎简单相加。该口径参考 [Microsoft GPU 指标说明](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/)。
- 显存：PDH `GPU Adapter Memory` 用量与 DXGI 适配器容量按 LUID 匹配；显示专用已用/总量，另列共享内存已用。多卡专用容量相加，共享上限仅是各驱动报告值，不能视为额外物理内存。共享用量已经使用系统内存，不能再与内存格相加。悬停可查看容量说明；核显的专用保留区也不是独立显存芯片。容量接口见 [DXGI_ADAPTER_DESC1](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/ns-dxgi-dxgi_adapter_desc1)。

0.1.34 起页面可见且停留总览或模块页时约每 3 秒请求；采样首次完成前短暂重试。服务器缓存 3 秒，同一实例最多一个采样线程，单次观察约 0.35 秒计数窗口，无常驻轮询线程。切换设置分页面、隐藏页签或离开页面即暂停前端轮询，在途采样可以收尾。后台慢采样不阻塞聊天 HTTP。数据缺失、驱动不支持或超过 15 秒未更新时显示“—/暂不可用”，不显示伪造的 0，也不把旧数据重新标为新值。暂未验证 Linux/macOS、全部显卡驱动或多卡实机；多引擎聚合有离线测试。接口见[资源快照契约](contracts.md#resource-usage-contract)，证据见[外观与资源验收](delivery-validation.md#appearance-resource-evidence)。

<a id="parallel-runtime-monitoring"></a>
### 并行运行与进程资源观测（0.1.34 implemented）

[RuntimeMetrics](../runtime/node-host/jarvis_core/runtime_metrics.py)是本机宿主内的有限观测对象，与既有 FIFO 共用事件。数据保留在内存，不另建数据库、监控进程或定时任务，不读取提示/回答正文、凭据、项目路径或任务参数。设置总览和模块页可见时复用原 3 秒按需刷新；统计按请求即时读取，整机/进程读数则来自同一有时间戳的有限采样。

| 指标 | 唯一口径与限制 |
|---|---|
| 聊天/任务活动数 | 聊天准入至真实处理线程退出；后台为宿主派发准入回调至执行器返回/清理。默认聊天 2 槽、任务 1 槽；正在清理的执行段可能比任务产物提交稍晚结束 |
| 完成耗时与排队 | monotonic 计时，P50/P95 按最近 200 个已结束样本的最近秩计算，聊天/任务分别统计，包含失败、停止与 UNKNOWN；不含首字/音频延迟。队列年龄用入队 UTC 到准入的墙钟差，包括人工暂停/停机，时钟跳变可能影响，负值截为 0 |
| 交叠、槽满与页面超时 | 交叠为任意聊天与任务同时活动的墙钟区间，不证明推理核并行执行。429 记槽满；504 记页面等待超时，不强制结束真实处理，不释放仍占用的槽，也不自动重发。线程启动失败释放占用并记录失败 |
| 恢复状态 | 队列暂停、内存不足/恢复等待、宿主所有权与未核对 UNKNOWN 从原账本/准入快照读取，不创造新 Task 状态。查看统计不推进准入或解除暂停 |
| 进程内存 | 只读取当前宿主及本实例持有的本地引擎进程；显示工作集与私有提交。不是完整进程树，未包括托盘、瞬态 Worker、浏览器和外部模型服务。工作集可能共享，不能简单相加为总物理占用；私有提交也不等于驻留 RAM |
| 进程 CPU | GetProcessTimes 的内核+用户 CPU 秒差除以采样墙钟与逻辑核数量，显示整机归一百分比；可与以一个核心为 100% 的证据读数不同。两次读取核对进程创建时间，进程消失/读数失败显示未知；不枚举或接管其他进程 |
| 生命周期与能力 | 结束样本有界，启动计数与事件计数属于本次宿主生命周期，重启后清零。记录中的 SUCCEEDED/CONFIRMED 是处理/回执状态，不能用它判定模型答案正确。没有新增自动抢占、模型优先级或 OS 资源租约 |

进程接口依据见[S170](references.md#s170)。原整机数值与缓存失效规则仍归[整机资源](#machine-resource-usage)。演示与恢复证据归[0.1.34 验收](delivery-validation.md#parallel-runtime-evidence)；目标普通 PC、长时压力、全部子进程与实际 OOM 恢复尚未验证。

<a id="dialogue-runtime-monitoring"></a>
#### 对话与语音分离后的观察增量（proposed）

复用上述面板和有界采样，增加控制/输入/回复/STT/TTS/工作/维护的活动数、队列年龄、实际占用与等待原因，显示模型冷/热状态和后端配额域。将模型首字、语音轮次结束、TTS 首音、客户端播放开始和停止分开计时；显示后台吞吐与最长等待，避免只优化聊天指标却让工作停滞。预算目标和测试定义只在[V-DLG](delivery-validation.md#conversation-separation-validation)维护。

0.1.48 已在现有设置的“并行运行与延迟”面板显示回复活动数、结果缓存数、预留 MiB 和已用编号；正文不进入监控。回复执行仍计入原聊天延迟/完成/停止统计，控制和缓存路径不创建额外常驻采样线程。0.1.49 另显示持久恢复的初始化状态；内存缓存数量仍只统计当前实例，不能当作磁盘字节数。它只验证[回复回执子集](delivery-validation.md#dialogue-receipt-evidence)及[恢复](delivery-validation.md#dialogue-recovery-evidence)，不代表下列整条语音链路均已监控。

排队、加载、识别、生成、播放、降级与故障分别可见；窗口关闭不新增常驻高频采样器，监控不可用也不能阻止控制/任务工作。指标只保留标识、用途、时间、状态和资源，不默认记录用户音频、倾诉正文或模型提示。当前面板只增加上述回执字段，完整语音/公平调度字段仍未具备；原有限进程范围不能冒充全系统覆盖。

0.1.51 增加“对话模型进程”卡片：显示运行数/槽位、实际 PID、运行秒数、工作集、单进程提交上限和最近退出原因；空闲为 0，不常驻推理服务。工作集与 384 MiB 提交上限含义不同，也不代表本地 LLM 权重或 GPU 占用。只查询本实例拥有的最多两个进程；不扫描整机、不记录聊天正文。字段由 `runtime.dialogue_processes` 提供，使用既有可见页面采样周期；退出/读数失败时不复用旧内存。完整边界见[契约](contracts.md#dialogue-process-contract)。

0.1.54 同一面板另显示“后台模型进程”，并为两类进程区分“准备上下文/等待模型/启动中”。后台字段是 `runtime.background_processes`；只代表接入的目录规划、技能报告和解释，不包括全部 Agent、维护与网页规划。阶段超时显示具体原因；界面没有新增任意结束 PID 的权限。限额与协议只在[进程契约](contracts.md#dialogue-process-contract)维护。

<a id="observability-2"></a>
### 追踪关联

使用 trace_id 关联 session → goal → task → agent → model_request → action → artifact → release。日志默认遮蔽凭据和敏感正文，按数据范围限制节点可见性。

OpenTelemetry 可承担追踪、指标和日志信号的互操作，项目仍需定义业务事件与保留策略。[S27](references.md#s27)

<a id="observability-3"></a>
### 资源策略

首先保留独立监督与设备安全停止资源，再预留交互资源，然后分配正式任务与进化实验。
- 单机没有足够资源时，降低模型规模或并发，而不是假设隔离进程能产生额外算力。
- 节点上报 CPU、内存、GPU/显存、存储、电量与温度允许范围。
- 跨设备任务优先迁移工作，不默认合并显存；分布式模型推理属于独立后期工程。
- 工具和模型缓存设上限；磁盘不足时暂停生成新产物并保留恢复所需空间。
- 模型下载、依赖安装和升级包准备有明确预算与离线缓存策略。

<a id="observability-4"></a>
### 备份与恢复演练

定期备份身份元信息、策略、记忆、任务账本、技能版本和产物引用。凭据按照系统密钥存储的备份能力单独处理。

恢复演练必须验证：身份仍可识别、记忆可检索、任务可接续、未知动作被标出、旧密钥权限不被意外复活。仅“备份命令成功”不足以证明可恢复。

<a id="system-health"></a>
## 长期健康与结构治理



<a id="system-health-4"></a>
### 怎样防止破坏已经有效的结构

**保护的是经过验证的结构性质，不是永远不许改变文件夹或框架。** 当前架构也可能有问题；要允许有证据的结构改进，同时禁止不知不觉地破坏边界。

把关键结构写成版本化、可执行的架构约束。演进式架构中的 fitness functions 提供了持续检查关键性质的思路；本项目据此设计下表，不宣称这些检查已经实现。[S56](references.md#s56)

| 要保护的性质 | 检查方式 | 不通过时 |
|---|---|---|
| 领域层不依赖具体 LLM/UI 框架 | 静态依赖图、禁止导入规则、构建边界 | 拒绝候选发布 |
| 模块不绕过自有 API 读写别的状态 | 代码审查、访问测试、数据库文件权限 | 拒绝并定位越界路径 |
| 只有指定入口可执行真实效果 | 网络/文件/桌面负向测试、短期能力校验 | 阻断；实际控制完整性违规按 G0 处理 |
| Task Runtime 唯一调度 | 并发、重复消息、重启和迁移测试 | 保留旧版本 |
| 新版本兼容存量任务与数据 | schema/契约兼容检查、旧检查点回放、迁移演练 | 标为需迁移，不能直接上线 |
| 前台交互资源受保护 | 同负载首响/打断和内存峰值对比 | 限流、降级或拒绝 |
| 任意已发布包有来源和恢复路径 | 包清单、摘要、来源记录、回退演练 | 不允许准入 |
| 变化没有无解释扩大复杂度 | 模块/依赖变化、重复实现、圈复杂度与维护负担检查 | 要求拆小改动或说明收益 |

Python 可以用 Import Linter 等工具检查指定层级的导入方向 [S57](references.md#s57)；其他语言接相应检查器。静态工具看不到所有动态加载和运行时权限，所以必须结合契约测试与实际隔离验证。

架构规则本身也可提出更新，但必须给出新旧规则对比、理由、迁移路线、验证与独立批准。候选不能通过删除检查、扩大白名单或提高阈值来“修复”违规；例外需有范围、负责人和到期条件。

<a id="system-health-5"></a>
### 一次变更的完成标准

一次改进只有同时满足以下条件才算完成：

1. 有明确问题、预期收益、基础版本、允许变更范围和撤销条件。
2. 代码和生成产物可以从固定输入构建，必要测试由独立环境通过。
3. 所有受影响契约、技能说明、配置 schema、操作文档、迁移和恢复说明同时更新。
4. 删除或退役被替代实现，或明确它仍需保留的用途、引用与到期条件。
5. 没有新增无主文件、无法追溯的依赖、生产调试入口、凭据输出、禁用测试或失效文档链接。
6. 新旧版本组合经过兼容验证，真实灰度没有触发既定退化门槛。
7. 评估、采用/拒绝和恢复证据写入改进账本。

每次发布绑定一个 ReleaseManifest：代码包、模型/技能兼容范围、配置、数据库 schema、有效文档集和评估版本。**不能代码已是 v3，运行时却检索 v1 的安装说明并据此自修改。**

单次变更设置最大影响范围与预算，默认优先小步；跨模块重构必须作为一个变更集联合评估，不能让多个各自“通过”的补丁任意组合。候选绑定基础版本，发布前核对；基础已变化则重新合并和验收。

<a id="system-health-6"></a>
### 代码、文档、调试材料如何分区

| 区域 | 用途 | 是否允许生产加载/正式检索 |
|---|---|---|
| source | 当前正式源代码及有效文档 | 仅通过构建/发布使用；不是在源码目录直接热改运行 |
| candidate | 正在研发的补丁、临时测试和实验记录 | 否 |
| packages/releases | 已批准的不可变运行包 | 仅激活清单指定版本 |
| debug/scratch | 临时日志、诊断脚本、中间产物 | 否；有范围、容量与保留期限 |
| quarantine | 来源不明、兼容失败或待调查对象 | 否；需要独立准入才能恢复 |
| archive | 退役版本、旧文档、失败实验证据 | 默认不进入当前知识检索，只用于追溯/恢复 |
| recovery | 已验证恢复包、信任材料和必要配方 | 受保护用途，普通清理不能删除 |

不得通过扫描任意目录自动发现并执行新插件，也不能把所有 Markdown 都塞入正式检索。插件和文档从激活清单加载；归档、草稿、调试、第三方引用和模拟资料必须带状态。源码历史可以保留在版本管理中，不需要长期在生产目录留下 `old/`、`new2/`、`final-final/` 等未登记副本。

生产诊断按需、限定时间启用；诊断端口、调试开关、详细日志和临时凭据必须在发布检查中核对。用于恢复或审计的证据不是垃圾，不能为了目录整齐或健康分数好看而删除。

<a id="system-health-7"></a>
### 安全退役与垃圾回收协议

没有静态引用不等于没有用途：配置、反射、插件注册、旧任务、迁移、回退版本以及离线节点都可能仍依赖旧对象。

RetirementRecord 至少记录：对象摘要、所属模块、被替代版本、已知引用、在途任务、兼容窗口、回退需要、离线节点支持期限、保留类别、审批范围、最早可删除时间与验证结果。

退役按顺序进行：

1. 标记 deprecated，禁止新任务创建新引用，当前引用继续受支持。
2. 结合声明依赖、发布清单和真实使用记录核对引用；不确定则延后。
3. 排空任务、完成必要迁移，并验证回退链与恢复包仍完整。
4. 仅对不再影响活跃用户的对象撤去加载入口或隔离，经过观察期。
5. 再次检查引用和保留要求，按预授权清理策略删除具体对象。
6. 写删除清单与最小审计记录，验证运行和构建没有依赖缺失。

需要防止检查与删除之间新增引用：用对象代际、退休锁和原子状态转换阻止重用，执行前重新核对摘要/身份。路径解析须验证真实路径仍在允许区域内，处理符号链接、junction、硬链接和路径替换；目录名包含“tmp”不能自动获得删除资格。

不允许清理未结束任务、UNKNOWN 动作的相关回执、未解除安全事件、有效回退包、必要迁移历史、主人原始资料和待传播删除记录。备份保留与主人删除请求按[记忆、知识与数据同步](knowledge-learning.md#memory-data)处理，不能无限备份已要求删除的正文。

离线节点不会让所有版本永久不退役：发布明确支持窗口与最低兼容版本，节点回来后按保留的迁移/重新配对路径升级；不能直接删除它恢复所需的唯一材料。过期但仍有未完成任务的节点按任务支持政策解决，不把时间到期当成任务已完成。

<a id="system-health-8"></a>
### 持续体检检查什么

健康不能只看“进程活着”。HealthReport 按领域报告状态、证据、新旧变化、影响范围、建议和可自动处理范围：

| 领域 | 典型检查 |
|---|---|
| 运行 | 心跳、队列停滞、取消能否生效、重启次数、任务超时 |
| 结果 | 固定哨兵任务、真实产物正确性、未知结果积压、用户纠错 |
| 数据 | 数据库完整性、引用一致性、索引与来源版本、备份可恢复性 |
| 架构 | 依赖越层、循环依赖、跨模块写入、重复权威、接口漂移 |
| 代码和包 | 未登记文件、依赖来源、活动版本、调试入口与孤立产物 |
| 知识和文档 | 过期说明、错误来源、事实冲突、旧版文档误检索、规则被普通知识覆盖 |
| 模型/技能 | 质量下降、能力声明不符、工具格式变化、资源和成本异常 |
| 安全控制 | 锁存可验证、权限/发布完整性、受限环境边界、未授权外发迹象 |

低成本运行观察、变更检查、结果回归和恢复演练采用不同的触发条件；下一版的完整分层、建议初值、缓存和延期语义统一见[自检计划](#inspection-scheduling)。确切频率仍需按硬件、覆盖要求和实测预算调整，不能为每个领域再维护一套独立固定心跳。

上表是完整维护设计，不能整体视为已运行。0.1.37 / evolution-v1 已实现一个限定对象的进程内周期检查、真实结果核验、候选修复和回退，范围、周期、故障去重、资源与保留限额统一见[限定成长闭环](evolution-release.md#bounded-evolution-loop)。它没有创建操作系统或 Codex 的定时任务，也不扫描全仓库或自动整理知识库。其他健康领域仍待实现。检测开销本身受预算约束；不可为了体检占满交互资源，或每天让大模型无目标重写代码。

<a id="inspection-scheduling"></a>
### 自检怎样触发，为什么不让大模型每五分钟检查

**proposed；替换计划，不改变当前 300 秒实现。** 自检先采用确定性探针和已有运行证据。当前原型每轮读取活动包及三个文件的摘要、版本/验收绑定，再启动一个受限 Worker 跑保留样例；v1 为 8 例，v2 为 12 例，覆盖排序、空输入、中文、转义、重复路径和 100 条清单。它不检查整台 PC，不扫描用户项目，不访问互联网核验新知识。健康且满足目标版本时不调用模型，所以该轮 token 为 0；隔离进程和文件校验仍消耗 CPU、磁盘与短时内存。连续运行且不忙时，300 秒约对应每日 288 轮常规检查，另有启动检查；这不是必要的产品要求。

下一版由每个探针声明触发事件、最大陈旧时间、缓存键、执行代价、观察范围与失败语义，统一调度，禁止每个标签各开一个定时线程：

| 层次 | 触发与建议初值 | 具体工作 | 模型与副作用 |
|---|---|---|---|
| 运行观察 | 复用任务开始/完成/失败、组件退出、网络变化、现有资源采样 | 更新错误率、队列与资源变化，不追加模型心跳 | 0 token；不执行修复 |
| 增量检查 | 包/配置/验收器/环境变化、发布后、真实结果失败；合并短时间重复事件 | 对受影响对象查清单、摘要、契约和少量哨兵输入 | 0 token；样例在隔离 Worker 执行 |
| 兜底巡检 | 无可靠变化事件时，建议 30 分钟轻量兜底；允许 5—360 分钟或关闭周期项 | 轮转检查有期限的登记对象，不做全盘扫描；连续稳定可退避至 6 小时 | 0 token；“下次”同时显示触发理由与到期条件 |
| 深度验证 | 发布前必须；普通维护建议最多每日一次、空闲时对到期对象运行，可改为每周或手动 | 回归、文档/依赖约束、选定数据一致性；各探针限时，不默认全库重建 | 默认确定性；必要的 AI 分析独立立项 |
| AI 辅助诊断 | 出现规则无法解释的异常或主人主动要求，且该用途策略允许 | 解释最小证据，输出假设与建议；不自行执行建议 | 才使用自检模型档案并记账；“无结论”仍是无结论 |

上述数值是起始配置，必须通过[成长验收](delivery-validation.md#growth-center-validation)的目标 PC 测量再调整，不能承诺固定开销。轻量巡检复用已存在指标；重型样例在前台繁忙、内存不足或电量策略不允许时延期，不挤占聊天。到达最大陈旧时间仍不能执行，显示“检查已过期 / 等待资源”，不能沿用旧绿色状态。休眠唤醒合并遗漏检查，不补跑整夜次数；重启保留到期时间，避免每次启动都发动一次付费诊断。

缓存键至少绑定对象摘要、契约、验收器和执行环境版本；命中缓存须显示“复用某时的检查”，不得伪装为刚执行。真实任务仍核验自身结果，不能用健康缓存放行错误产物。手动“立即自检”可选择快速/深度并绕过相应缓存，但不顺带修复。UI 刷新只是读缓存，与后台检查频率和模型调用频率是三个不同概念。

<a id="healing-incident-policy"></a>
### 自愈围绕故障，进化围绕目标

故障先分类：代码/包退化、环境与资源不足、提供商故障、未知结果、数据/控制完整性问题。仅一个任务失败不足以认定代码有缺陷；需核对输入、前提、执行回执与基线。模型余额不足进入路由恢复，不触发重写工具；内存不足进入等待资源，不制造“修复代码”任务。

每个 incident 按“对象 + 基线 + 故障签名”去重，累计出现次数和证据；只有一个修复负责人和发布租约。自愈先尝试已验证且适用的恢复配方（例如恢复上一可用包）；无配方且确需改代码时生成**恢复既有契约**的候选。两个标签可同时观察，但同一对象的修复与进化不能并发发布：修复优先，进化重新核对基线后再继续。使用既有 H0—H4 分级，不另造一组等级。

“已处理”分为恢复动作完成、原故障复测通过、观察期结束三个阶段。复发重新打开同一事件或关联后续事件；版本来回切换达到阈值时停止该对象自动切换。取消和手动回退是主人覆盖决定，定时任务不能立即撤销；暂停范围、原因和恢复条件必须持久化。只有自愈策略可接受故障事件，自检报告本身不是执行授权。

<a id="system-health-9"></a>
### 分级自愈与停止边界

| 级别 | 情况 | 可自主操作 | 不能做什么 |
|---|---|---|---|
| H0 观察 | 状态波动或证据不足 | 采样、记录、定位、冻结有风险的相关动作 | 将“不确定”当成允许高风险行动 |
| H1 确定性恢复 | 无安全锁存的普通可恢复故障 | 按已验证配方重启受影响 Worker、重连获准服务、清理已确认可回收缓存 | 无限重启、扩大权限或删除未知数据 |
| H2 候选修复 | 已定位缺陷、需要代码/技能修改 | 建立改进单，隔离编程、评估、灰度 | 原地修补生产，跳过测试或修改验收阈值 |
| H3 降级/回退 | 新版退化或多次修复失败 | 回到经验证的兼容发布组合；暂停该自动修复方向 | 只回滚一个文件却忽视数据库/配置依赖 |
| H4 维护等待 | 无可用恢复组合、不可逆迁移或需新权限 | 保存最少状态、降级只读/待机，给出具体维护提案 | 假装修好，擅自扩大资源或重新解释主人授权 |
| G0 锁存 | 确认根原则违规或失去可信控制 | 仅[主人利益最高原则、独立监督与锁存关停](security-sovereignty.md#sovereignty-shutdown)固定停止、告警、审计和主人解锁验证 | 自诊断修复、运行编码模型、自动回退或自启动业务 |

H0—H4 服从 G0；不是一种可以绕过安全关停的替代路径。即使某次攻击被 OS 隔离阻止，只要确认它是系统自身生成的真实违规计划，仍按既定 G0 分类处理。

普通自动修复采用每对象有限尝试、退避和观察期，次数及共享预算统一由[用途预算](models-offline.md#growth-budget-policy)配置；超过限额触发降级或维护等待。对于设备动作、计费和 UNKNOWN，先查实际效果，不用重试修复造成重复执行。自动恢复只能在当前授权范围内工作。

<a id="system-health-11"></a>
### 避免多个 Agent 同时“治疗”同一故障

Health Controller 只汇总证据、提出维护任务，不另建可直接修改生产的超级权限。普通恢复仍由 recovery-supervisor 执行；代码修复仍由进化任务、构建器和发布器完成；知识修复通过 Memory API；清理由已批准的退役清单驱动。

每个受影响模块或兼容变更集有唯一 repair_id 和负责人，绑定 base_release、资源锁、预算、证据和截止时间。重复告警合并为同一事件；多个 Agent 可以并行分析，但只有被授权的变更集能进入发布。失联修复者通过代际和任务状态取消，不能与接管者同时写生产。

多个版本互相反复回退属于异常，应记录抖动和根因、冻结自动切换；不能让 Supervisor、模型路由器和拓扑管理器各自“修好”却互相破坏。

<a id="system-health-13"></a>
### 恢复能力与不可承诺的事情

可靠自愈不等于系统永远不“生病”。隐藏缺陷、未知攻击、错误基线、硬件损坏和不可撤销外部效果仍可能无法自动修复。备份成功也不等于恢复成功，需要实际演练。

采取稳定运行、隔离候选、独立恢复三条路径，并保留可验证的干净安装材料。怀疑生产目录污染时，优先从已验证清单重建运行环境，不在被污染目录中无限补丁叠加。恢复时只导入经校验的必要数据与有效配置，不能把整个可疑目录一并复制回来。

数据库结构已发生不可逆迁移时，必须使用事先设计的前向恢复、兼容快照或维护方案；不能无条件“装回旧程序”。已发生现实损害如实披露并处理，恢复代码不等于撤销现实效果。G0 事件仍按[主人利益最高原则、独立监督与锁存关停](security-sovereignty.md#sovereignty-shutdown)由主人解除后才恢复业务。
