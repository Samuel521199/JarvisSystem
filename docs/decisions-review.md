## 关键架构决策与待验证问题



<a id="architecture-decisions-1"></a>
### 当前建议采纳的决策

| ADR | 决策 | 理由 |
|---|---|---|
| ADR-001 | 完整节点 local-first | 直接满足断网独立 Jarvis |
| ADR-002 | 记忆最终一致，关键行动明确所有权 | 兼顾自治与副作用正确性 |
| ADR-003 | 不让所有设备参与共识投票 | 手机和笔记本不稳定在线 |
| ADR-004 | 生产/维护隔离，独立恢复入口 | 防止进化拖垮交互或失去自救 |
| ADR-005 | 语言中立契约；小型 Rust 底座、Python 业务/Worker、按需 TypeScript UI 为参考 | 先减少实现与维护成本，语言迁移需相同验收与收益证据 |
| ADR-006 | 框架只做适配器 | 身份和数据不绑定单一供应商/框架 |
| ADR-007 | 模块包不可变，生产版本不原地修改 | 支持并行版本、审计与恢复 |
| ADR-008 | 长任务版本固定、动作授权实时检查 | 兼顾可复现与撤权生效 |
| ADR-009 | 按服务等级承诺连续性 | 明确物理与单机条件，避免虚假零中断 |
| ADR-010 | 自主进化通过外部评估与发布控制 | 防止生成者自证并直接覆盖生产 |
| ADR-011 | Windows 服务与用户会话助手分开 | 符合实际操作系统边界 |
| ADR-012 | 首期指定协调节点，不急于集群化 | 尽早验证正确性与用户体验 |
| ADR-013 | G0 和锁存优先于可用性/进化 | 防止自动恢复继续已禁止行为 |
| ADR-014 | 人格、Agent 身份、Worker、模型解耦 | 支持动态生成和资源复用 |
| ADR-015 | 模拟与现实知识/能力分域 | 避免虚构污染与现实动作越权 |
| ADR-016 | 本地模型组合与确定性底座并存 | 资源不足时保留有用功能与可靠停止 |
| ADR-017 | 首期关键控制状态共用本地事务，逻辑模块唯一写入 | 明确任务、预算、动作与 outbox 一致性 |
| ADR-018 | 运行、构建、独立验收分离，工具链按版本扩展 | 支持离线自主开发而不把编译器变成生产依赖 |
| ADR-019 | 单一任务调度权威，其他控制器职责明确 | 避免重试、扩容、发布与恢复彼此竞争 |
| ADR-020 | 本地事实/原件与可重建检索索引分离 | 记忆框架与向量引擎可替换，不因重新嵌入丢失来源和纠正；见[选型](stack-project-layout.md#memory-open-source) |
| ADR-021 | 共同体复制领域事件，不共享活跃数据库文件 | 保留断网自治、作用域与可解释冲突；CRDT 按数据类型使用；见[同步协议](federation.md#memory-replication) |
| ADR-022 | 嵌入空间、提取器与索引代次分别固定 | 允许资源不同的节点构建不同索引；影子验证后切换，不以回退复活删除；见[记忆契约](contracts.md#memory-provider-contracts) |
| <a id="adr-023"></a>ADR-023 | 普通 PC 优先、能力按需加载、默认组件收敛 | **accepted，2026-10-15 主人明确要求**；默认部署与新增组件准入见[唯一规则](stack-project-layout.md#technology-selection-4)，资源验收见[PC 开销验收](delivery-validation.md#pc-footprint)；不把已采纳的约束误记为性能已验证 |
| <a id="adr-024"></a>ADR-024 | 首个固定计算 Worker 使用 Windows 原生 LPAC/Job，按任务启动 | **implemented/verified 子集，0.1.7**；不增加常驻编排器或第三方沙箱；约 22 MiB 运行包换取进程/文件/网络隔离。限制与剩余风险归[安全页](security-sovereignty.md#worker-isolation)，证据归[验收页](delivery-validation.md#worker-evidence)；不是通用生成代码执行器或跨平台完成声明 |

<a id="architecture-decisions-2"></a>
### 开工前的验证清单

| 问题 | 默认设计 | 何时必须确认 |
|---|---|---|
| 主机硬件与最低离线模型 | 已有开发机和[小模型组合](models-offline.md#configured-models)；嵌入及最低节点配置仍待比较 | M0 性能基线及 V-MEM 选型实验 |
| 是否需要整机全程离线 | 支持离线；外部请求由资料策略决定 | 接入首个云模型前 |
| 实际设备与软件清单 | Windows 与本地文件优先 | 相关适配器开发前 |
| 语音与角色形象 | 使用获授权声音和可配置角色 | 语音/形象接入前 |
| 自主工作额度 | 以任务和维护预算明确约束 | 开放后台执行前 |
| 共同体主机是否长期在线 | 首选家中稳定 PC 或服务器 | M3 |
| 哪些资料可以跨设备/进云 | 默认设备本地，按需开放 | 同步与外部模型启用前 |
| 可接受的维护暂停 | 分功能制定 C0—C3 | 进入生产升级前 |
| 模型及组件许可 | 锁定依赖时审阅适用许可 | 分发与商业使用前 |
| 实物控制范围 | 先读状态、再预览、再控制 | 接入实体执行器前 |

这些问题不妨碍完成本设计，但影响后续具体型号、成本、并发和实施范围。

<a id="architecture-decisions-3"></a>
### 最大的工程难点

1. 多步骤任务的可靠验证，比生成计划更困难。
2. 离线自治和全局唯一动作之间存在必须取舍的边界。
3. 自主进化的关键瓶颈是评估和恢复，而不仅是写代码。
4. 语音实时性取决于硬件、模型和资源管理，不能只靠异步代码。
5. 记忆需要保留事实来源和纠错机制，避免把反复生成的推测固化为事实。
6. 每增加一个软件或设备，都增加适配、授权、观察和故障处理工作。
7. 长期运行需要治理数据增长、过期版本、成本与依赖退役。

<a id="critical-review"></a>
## 批判性评审、评分与更好的设计取舍



<a id="critical-review-1"></a>
### 评审对象与结论

**被评分的是 2026-10-15 对原 v0.2 设计的历史快照；加权设计成熟度为 68/100。产品性能、可靠性和实际自主能力暂不评分，因为没有本项目原型或实测结果。**

这个分数表示：需求覆盖和总体方向有价值，但还不能按几十个模块直接全面开工。后续设计根据问题补充机制并缩小首期实现；不能因为文档加了章节，就自动提高安全、性能或落地得分。

本轮将分布式/权限、技术栈/实现成本、工具链审查分别进行，独立意见约为 65—68 分；最终采用下表公开权重，避免挑选最高评价。它们仍属于同一 AI 辅助设计过程，不是外部专家审计、认证或统计测量。参考 ATAM 的方法，比较质量属性的冲突与风险；本评审没有执行正式完整的 ATAM 工作坊。[S40](references.md#s40)

评分尺度：0—2 表示机制缺失或明显冲突；3—4 表示原则多于落地路径；5—6 表示方案可讨论但关键选择未闭合；7—8 表示较具体且有取舍；9—10 需要主要边界、成本和验证闭环都足够清楚。分数用于暴露差距，不用于宣传“智能程度”。

<a id="critical-review-2"></a>
### 设计评分表

| 维度 | 权重 | v0.2 得分 /10 | 加权贡献 /100 | 主要扣分 |
|---|---:|---:|---:|---|
| 需求覆盖与产品边界 | 15% | 8.0 | 12.00 | 首期范围仍大，核心日常任务未固定 |
| 模块职责与控制权 | 20% | 6.5 | 13.00 | 资源、团队、拓扑、发布、恢复的权威界面不够具体 |
| 分布式与数据语义 | 15% | 7.5 | 11.25 | 已考虑分区和 UNKNOWN，但预算/任务/动作事务未落定 |
| G0 与实际权限执行 | 15% | 6.0 | 9.00 | 有锁存规范；语义风险判断和 OS 边界尚无验证 |
| 升级与自主进化 | 10% | 7.0 | 7.00 | 缺实际发布矩阵、构建闭包和长期退化证据 |
| 工程复杂度与实施成本 | 10% | 5.5 | 5.50 | 多语言、多控制循环与大量前置抽象增加维护负担 |
| 可测试性与验收设计 | 10% | 7.0 | 7.00 | 有故障用例，缺冻结的任务基线和误报/漏报测量 |
| 架构视图与决策追溯 | 5% | 6.5 | 3.25 | 总逻辑图不能代替部署、权限、状态和构建视图 |
| **合计** | **100%** | — | **68.00** | **适合作为目标架构，尚不是完成的工程实现** |

构建与多语言能力在 v0.2 的单项诊断约为 4/10；其缺陷已经计入升级、实施成本和架构视图，不再重复加权。改变权重会改变总分，因此必须同时看扣分原因。

<a id="critical-review-3"></a>
### 证据成熟度：设计不等于产品成绩

以下 EV 级别专指验证证据，不与[自主进化与自我重构](evolution-release.md#self-evolution)进化等级 E1—E6 混用。

| 级别 | 所需证据 |
|---|---|
| EV0 | 只有目标或待研究假设 |
| EV1 | 有设计机制、接口或相关外部依据 |
| EV2 | 本项目原型可运行，保存正常场景记录 |
| EV3 | 可重复测试、故障注入和独立评估通过 |
| EV4 | 实际长期运行，有质量、成本和事故统计 |

离线运行、共同体对账、持久任务、升级回退、动态 Agent 和工具开发当前均为 **EV1**；“开放语义下识别任何主人利益损害”和“长期进化一定产生净收益”仍有 **EV0—EV1** 成分。本文未提供 EV2 以上产品证据。论文、成熟框架和新增架构图不能替代 Jarvis 自身验证。

因此目前可以说“设计具备这些能力的扩展路径”，不能说“已经达到电影级智能、已经绝对可靠或一定比所有单模型更强”。

<a id="critical-review-4"></a>
### 六个实质问题及本版处理

| 问题与具体后果 | 本版改动 | 尚未闭合的验证 |
|---|---|---|
| 多个控制器可能反复重启、休眠和迁移同一 Worker | [控制器的唯一权威：消除相互抢控制](architecture.md#architecture-runtime-5)指定唯一权威与建议边界 | 同时升级、限流、崩溃和取消的竞争实验 |
| “模块各有状态”没有说明跨预算/任务/动作事务 | [补齐架构视图：每张图回答不同问题](architecture.md#architecture-runtime-4)固定首期 control.db；[补足预算与委派协议](tasks-agents.md#critical-review-6)定义预留/委派 | 崩溃点、晚到回执和分区实验 |
| G0 开放语义不可能仅靠提示词证明；过于粗糙会误关停 | [判定结果、流式输出与可测量的边界](security-sovereignty.md#sovereignty-shutdown-11)区分判定结果、证据与流式放行 | 误报、漏报、绕过、延迟；不能据规则表宣称零风险 |
| 大量领域提前用 Rust、多种工作流框架增加维护成本 | [技术栈与选型理由](stack-project-layout.md#technology-selection)、[项目文件结构与依赖规则](stack-project-layout.md#project-structure)改为语言中立边界与精简参考实现 | 同硬件原型比较及维护成本 |
| 独立升级只描述原则，缺具体发布单元 | [发布单元矩阵](evolution-release.md#critical-review-7)建立发布矩阵 | 数据迁移、旧任务支持窗口和回退演练 |
| 语言扩展只有目录，没有开发工具链系统 | [自带开发环境与多语言自我开发平台](toolchains.md#development-platform)补构建、验证、依赖闭包、生命周期 | 离线重建、两语言替换、隔离攻击验证 |

本版把空白转成可实现且可验收的设计选择；表格“本版改动”不等于已经消除运行风险。

<a id="critical-review-5"></a>
### 必须接受的五组取舍

1. **离线可用与即时全域控制。** 分区节点不能立即得知远端撤权；仅在本地有效范围内自治，全局独占动作等待。统一身份是共同数据和协调的工程结果，不是任意时刻所有节点脑中完全一致。
2. **自主改造与稳定服务。** 改动越广、状态越多，迁移与独立评估越昂贵。热切换适用于满足条件的发布单元，单机 OS、驱动和不可迁移状态允许维护窗口。
3. **自我编程与可信控制。** 可生成任意候选源码，不代表它能直接改监督器、发布密钥或主人约束；对根控制实现的修改走主人维护入口，不允许自行批准降低规则。
4. **低资源与高能力。** 本地小模型可提供有用降级，但不能假设它自动拥有云大模型同等复杂推理；并行编译与 NPC 世界也消耗资源。
5. **快速语音与事前完整检查。** 分段放行可降低首响，但复杂内容可能需要整段检查。不能一边承诺任意低延迟，一边声称每个输出的所有长期影响已被完全验证。

G0 在这些取舍中仍最高；不能为了提高可用性分数而撤销用户要求的锁存关停。

<a id="critical-review-8"></a>
### 更好的方案比较

| 理念/架构 | 解决什么 | 代价 | 本项目选择 |
|---|---|---|---|
| 持久任务为中心的模块化应用 | 少数状态权威、离线好部署、形成真实工作闭环 | 同宿主模块可能一起发布 | **首期主结构** |
| 小型能力内核 + 受限插件 | 生成代码只能得到范围有限的资源访问，智能层可替换 | OS 隔离与能力粒度难；任意桌面控制尤其难约束 | **与首期主结构组合采用** |
| 资源单一所有者 + Actor/监督树思想 | 会话、设备、任务、NPC 生命周期更清楚 | 消息不自动持久，也不保证业务幂等 | **采用所有权思想；框架按需后置** |
| 全微服务 + 集群编排 | 多团队、大规模独立发布和服务容量 | 初期运维、协议、故障诊断成本高 | **后期有数据支持再引入** |
| 一个通用 Agent 直接管理整台系统 | 原型极快、演示灵活 | 规划、执行、权限、状态与自修改高度混合 | **仅隔离实验，不作为生产底座** |
| 所有扩展统一 WASI | 一类插件的接口、可移植性和权限更清晰 | 覆盖不了全部原生/桌面/专业库需求 | **可选载体，保留原生进程** |

能力内核的原则可借鉴最小权限、完全仲裁等保护系统思想 [S36](references.md#s36)；监督树可参考 OTP [S52](references.md#s52)，不要求为了借用思想而迁移到 Erlang。软件协议不能代替操作系统隔离；Actor 框架也不能代替动作账本。

长期更有价值的设计理念：

- **系统身份和记忆属于主人，模型只是可替换的计算器。** 换模型不必“换一个贾维斯”。
- **扩展能力通过版本化能力包表达。** 每包说明输入输出、实际效果、权限、资源、来源、验证和恢复，避免每个新功能都改内核。
- **只有行动意图才能进入执行链。** 输出已检查的结构化任务和效果声明；生成式内容本身不获得执行权。
- **环境信息和控制信息分开。** 互联网知识、陌生节点、插件描述和 NPC 叙事不能提升为授权。
- **进化以真实净收益计。** 在固定任务集比较质量、成本、延迟、故障与可恢复性；不能用自评高分、Agent 数量、知识库大小或代码行数代替进步。
- **自动化程度逐能力提高。** 某项任务可自主，不代表所有新任务继承同样权限；权限扩大需要独立准入。
- **保留退出与迁移能力。** 数据可导出、协议有说明、恢复工具不依赖单一模型和云服务；这比让系统无条件追求自身延续更符合主人控制权。
