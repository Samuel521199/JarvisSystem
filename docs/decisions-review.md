<a id="architecture-decisions-3"></a>
### 最大的工程难点

1. 多步骤任务的可靠验证，比生成计划更困难。
2. 离线自治和全局唯一动作之间存在必须取舍的边界。
3. 自主进化的关键瓶颈是评估和恢复，而不仅是写代码。
4. 语音实时性取决于硬件、模型和资源管理，不能只靠异步代码。
5. 记忆需要保留事实来源和纠错机制，避免把反复生成的推测固化为事实。
6. 每增加一个软件或设备，都增加适配、授权、观察和故障处理工作。
7. 长期运行需要治理数据增长、过期版本、成本与依赖退役。

## 批判性评审、评分与更好的设计取舍



<a id="critical-review-1"></a>
### 评审对象与结论

**本节保留 2026-10-15 对原 v0.2 设计的历史评分 68/100，不是当前产品分数。** 当时该评审没有纳入原型实测；当前 0.1.37 已有代码与验证，见[当前系统审计](#current-system-audit)。不能继续把历史“没有原型证据”用于描述现在。

这个分数表示：需求覆盖和总体方向有价值，但还不能按几十个模块直接全面开工。后续设计根据问题补充机制并缩小首期实现；不能因为文档加了章节，就自动提高安全、性能或落地得分。

本轮将分布式/权限、技术栈/实现成本、工具链审查分别进行，独立意见约为 65—68 分；最终采用下表公开权重，避免挑选最高评价。它们仍属于同一 AI 辅助设计过程，不是外部专家审计、认证或统计测量。参考 ATAM 的方法，比较质量属性的冲突与风险；本评审没有执行正式完整的 ATAM 工作坊。[S40](references.md#s40)

评分尺度：0—2 表示机制缺失或明显冲突；3—4 表示原则多于落地路径；5—6 表示方案可讨论但关键选择未闭合；7—8 表示较具体且有取舍；9—10 需要主要边界、成本和验证闭环都足够清楚。分数用于暴露差距，不用于宣传“智能程度”。

<a id="critical-review-3"></a>
### 证据成熟度：设计不等于产品成绩

以下 EV 级别专指验证证据，不与[自主进化与自我重构](evolution-release.md#self-evolution)进化等级 E1—E6 混用。

| 级别 | 所需证据 |
|---|---|
| EV0 | 只有目标或待研究假设 |
| EV1 | 有设计机制、接口或相关外部依据 |
| EV2 | 本项目原型可运行，保存正常场景记录 |
| EV3 | 可重复测试、故障注入和独立评估通过 |
| EV4 | 实际长期运行，有质量、成本和事故统计 |

在上述 **2026-10-15 历史评分口径**中，离线运行、共同体对账、持久任务、升级回退、动态 Agent 和工具开发仅按 EV1 讨论。当前部分固定任务、隔离执行及限定成长已达到 EV2—EV3，不能把这些局部证据外推到共同体、任意编程或 EV4 长期可靠性。“开放语义下识别任何主人利益损害”和“长期进化一定产生净收益”仍有 EV0—EV1 成分。当前证据范围归[验收章](delivery-validation.md#current-audit-evidence)。

因此目前可以说“设计具备这些能力的扩展路径”，不能说“已经达到电影级智能、已经绝对可靠或一定比所有单模型更强”。

<a id="critical-review-5"></a>
### 必须接受的五组取舍

1. **离线可用与即时全域控制。** 分区节点不能立即得知远端撤权；仅在本地有效范围内自治，全局独占动作等待。统一身份是共同数据和协调的工程结果，不是任意时刻所有节点脑中完全一致。
2. **自主改造与稳定服务。** 改动越广、状态越多，迁移与独立评估越昂贵。热切换适用于满足条件的发布单元，单机 OS、驱动和不可迁移状态允许维护窗口。
3. **自我编程与可信控制。** 可生成任意候选源码，不代表它能直接改监督器、发布密钥或主人约束；对根控制实现的修改走主人维护入口，不允许自行批准降低规则。
4. **低资源与高能力。** 本地小模型可提供有用降级，但不能假设它自动拥有云大模型同等复杂推理；并行编译与 NPC 世界也消耗资源。
5. **快速语音与事前完整检查。** 分段放行可降低首响，但复杂内容可能需要整段检查。不能一边承诺任意低延迟，一边声称每个输出的所有长期影响已被完全验证。

G0 在这些取舍中仍最高；不能为了提高可用性分数而撤销用户要求的锁存关停。

<a id="critical-review-8"></a>
### 更好的方案比较

| 理念/架构 | 解决什么 | 代价 | 本项目选择 |
|---|---|---|---|
| 持久任务为中心的模块化应用 | 少数状态权威、离线好部署、形成真实工作闭环 | 同宿主模块可能一起发布 | **首期主结构** |
| 小型能力内核 + 受限插件 | 生成代码只能得到范围有限的资源访问，智能层可替换 | OS 隔离与能力粒度难；任意桌面控制尤其难约束 | **与首期主结构组合采用** |
| 资源单一所有者 + Actor/监督树思想 | 会话、设备、任务、NPC 生命周期更清楚 | 消息不自动持久，也不保证业务幂等 | **采用所有权思想；框架按需后置** |
| 全微服务 + 集群编排 | 多团队、大规模独立发布和服务容量 | 初期运维、协议、故障诊断成本高 | **后期有数据支持再引入** |
| 一个通用 Agent 直接管理整台系统 | 原型极快、演示灵活 | 规划、执行、权限、状态与自修改高度混合 | **仅隔离实验，不作为生产底座** |
| 所有扩展统一 WASI | 一类插件的接口、可移植性和权限更清晰 | 覆盖不了全部原生/桌面/专业库需求 | **可选载体，保留原生进程** |

能力内核的原则可借鉴最小权限、完全仲裁等保护系统思想 [S36](references.md#s36)；监督树可参考 OTP [S52](references.md#s52)，不要求为了借用思想而迁移到 Erlang。软件协议不能代替操作系统隔离；Actor 框架也不能代替动作账本。

长期更有价值的设计理念：

- **系统身份和记忆属于主人，模型只是可替换的计算器。** 换模型不必“换一个贾维斯”。
- **扩展能力通过版本化能力包表达。** 每包说明输入输出、实际效果、权限、资源、来源、验证和恢复，避免每个新功能都改内核。
- **只有行动意图才能进入执行链。** 输出已检查的结构化任务和效果声明；生成式内容本身不获得执行权。
- **环境信息和控制信息分开。** 互联网知识、陌生节点、插件描述和 NPC 叙事不能提升为授权。
- **进化以真实净收益计。** 在固定任务集比较质量、成本、延迟、故障与可恢复性；不能用自评高分、Agent 数量、知识库大小或代码行数代替进步。
- **自动化程度逐能力提高。** 某项任务可自主，不代表所有新任务继承同样权限；权限扩大需要独立准入。
- **保留退出与迁移能力。** 数据可导出、协议有说明、恢复工具不依赖单一模型和云服务；这比让系统无条件追求自身延续更符合主人控制权。

| A-05 / 高 | [recipes.expected](../runtime/node-host/jarvis_core/evolution/recipes.py) 已完整实现目标转换；`_execute` 对每次生成结果与其比较。这能验证受限闭环，但宿主本身已经知道答案，无法据此证明新增了原本不会的能力 | 下一个实验必须有独立的真实任务收益，如受控检索模块在保留任务上提高召回且不增加泄露/成本；不要求把测试答案开放给候选，也不删除现有 oracle |
| A-06 / 中 | 静态 import 图存在 `memory ↔ memory_view ↔ knowledge`、`extensions ↔ mcp_catalog` 两组环，包括函数内导入；当前测试通过，因此不是“现在无法 import”的结论 | 抽出小型作用域类型/规则和 MCP 目录读取契约，让查询视图依赖存储接口，基础存储不回依赖编排层；用依赖方向检查阻止再生 |
| A-07 / 中 | [knowledge.py](../runtime/node-host/jarvis_core/knowledge.py) 每次请求有界读文件、词法评分，最多选 6 个片段；[context_assembly.py](../runtime/node-host/jarvis_core/context_assembly.py) 最近 20 条/32 KiB 历史，不生成摘要；“知道所有项目”还没有依据 | 先建立中文/代码/纠错检索基线，再增量索引或嵌入；长期事实、事件记忆与原始会话保持不同可信语义，不把全部历史反复塞进 prompt |
| A-08 / 中 | [EvolutionStore](../runtime/node-host/jarvis_core/evolution/store.py) 64 个包、1,000 条重要任务限额；当前只有健康检查压缩，没有候选引用分析/退役入口。限额能防无限增长，但长期达到阈值后停止成长 | 按既有退役规则保留活动/回退/在途引用及必要证据，提供可解释归档与空间预估；不能简单删除最老目录 |
| A-09 / 中 | [index.html](../apps/web/index.html) 内嵌主聊天状态；[workspace.js](../apps/web/workspace.js) 直接操作全局 history、DOM 节点及多个 window 对象；`server.py` 1,002 行承担资产、初始化、路由、请求校验和多领域调用 | 抽聊天会话状态和薄 API 客户端，按领域拆 route/组合入口；可先用原生 ES module 与类型检查，无需同步重写 React/后端 |
| A-10 / 中 | 存储各有事务和版本，但目前没有共同体的可重放领域事件、inbox 去重和完整跨库恢复协议；“多份 SQLite 文件”本身不是错误，`snapshot_atomic=False` 已诚实声明 | 保留各领域唯一写入接口；只有确需共同提交的任务/资源/动作意图共用事务；同步复制领域事件，不让设备共享活跃 `.db` |
| A-11 / 中 | 相同 0.1.37 下包含多轮代码增量；若只记录版本号，历史探测不能准确绑定当前工作树。旧评审曾仍写“没有原型”，架构表仍写原生技能未实现 | 发布和评估绑定源码/契约/配置摘要；本轮已纠正文档漂移，未替用户提交代码或清理未跟踪文件 |

正面事实也应保留：输入 schema/范围检查、结构化 UNKNOWN、迟到结果取消、引用摘要、幂等请求、OS 级受限执行和失败不覆写当前版本，都比“只给通用 Agent 一个终端”更接近可维护助手。没有发现证据支持“代码已经不可修复”或“必须全部重写”。

<a id="current-architecture-choice"></a>
### 更好的架构与实施取舍

**推荐：以持久的个人助手核心组织体验，以模块化单体承载实现，以能力包扩展工作与行动。** 身份/表达、适用记忆、交流与注意力在中心；任务执行、项目编辑、成长、Agent 和设备通过明确接口接入。按故障与权限边界使用按需进程，以本地事务加领域事件支持未来同步。完整结构只维护在[PC 架构设计](architecture.md#pc-runtime-convergence)，不复制另一套核心或开发时间线。

| 选择 | 对本项目的收益 | 代价 / 判断 |
|---|---|---|
| 继续按功能追加 if 分支和页面 | 短期交付快 | 能力清单、预算与状态更分散；不建议保持这个增长方式 |
| **收敛后的模块化单体 + 能力包 + 持久任务** | 复用现有 Python/SQLite/Worker，单机可用，模块边界逐步可测 | 需要改接口和迁移验证；当前最适配，不等于已达到更高评分 |
| LangGraph 作为可选规划器 | 复杂推理图和检查点可复用成熟机制 | 工具副作用、预算、包发布、共同体身份仍需 Jarvis 负责；先接一个明确工作流，不整体替换状态权威 |
| Temporal / 大规模微服务 / K8s | 大量服务端长流程或多团队部署可能受益 | 增加 PC 常驻依赖与网络故障面；目前没有容量证据支持迁移 |
| Rust/Go/C# 重写核心、Tauri 重写外壳 | 原生集成或已测性能热点可能受益 | 不能自动解决记忆质量、规划正确性或资源冲突；先确定具体替换单元和同任务收益 |
| 所有模块 WASI 化 | 一部分纯工具接口与可移植性更清楚 | 原生桌面、模型引擎和专业库并不都适合；保持可选执行器 |

本轮复核了 [SQLite 官方适用范围](https://www.sqlite.org/whentouse.html)、[LangGraph 持久化](https://docs.langchain.com/oss/python/langgraph/persistence)、[Fowler 的模块化起步讨论](https://martinfowler.com/bliki/MonolithFirst.html)和 [OTP 监督树](https://www.erlang.org/doc/system/sup_princ.html)。它们分别支持本地低运维存储、区分推理检查点和长期数据、先稳定边界、按故障关系恢复的思路；**上述组合是本项目推导，不是这些来源替 Jarvis 做出的性能保证**。SQLite 单写者与网络文件共享限制尤其说明“先加集群数据库”不是当前问题的答案。来源登记见 [S188](references.md#s188)及既有 S11/S39/S52。

实施次序以[唯一 K0—K6 阶段表](core-bootstrap.md#bootstrap-5)为准：K1 继续修复会阻断交流的底座故障；K2 贯通个人会话、基础人格、明确记忆与接续、按需行动和最小受限成长。K3—K5 扩大研发与自身改造范围，多设备仍按 K6 验证。不能用代码生成演示代替个人体验，也不能只做会聊天的角色而遗漏自主成长。

下次评审先看主人是否不必重复介绍自己、纠正是否生效、模型切换后是否仍能接续、后台活动是否影响交流，再看真实任务收益与工程质量。可选页面损坏仍能聊天、统一能力准入、共同预算及 V-GROW 依然必要，原因是它们保障助手体验。代码数量、候选数量、模型名称和动画精细程度不能替代这些证据。
