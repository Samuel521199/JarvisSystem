## 1. 维护范围与入口

当前设计以 [文档入口](README.md) 和 `docs/manifest.json` 登记的有效文件为准。根目录 README 只提供入口，根目录 AGENTS 说明后续 AI 的工作约定。主题页共同组成一套设计，不再维护平行的总设计全文、核心全文副本或旧版本归档目录。

本文管理文档本身；[系统健康与维护](health-maintenance.md) 描述未来 Jarvis 的体检、抗退化、退役和自愈，两者不得混为一谈。修改文档不等于启用系统自愈、定时检查或后台自动任务。

若已使用 Git，历史由版本记录保存；未使用 Git 时，可按用户明确要求使用外部受控历史。不得仅为本次文档维护自行初始化 Git，也不得把旧全文复制回当前文档树充当备份。系统运行时需要保留的恢复包、审计和迁移证据，仍按相应系统设计处理。

<a id="single-authority"></a>
## 2. 每项内容只有一个权威位置

每个概念、规则、完整流程、目录树或验收定义只有一个维护位置。其他页面可以用短摘要帮助阅读，但必须链接到权威位置，不复制可独立修改的完整定义。

完整的权威页面地图只维护于 [文档入口](README.md)，避免这里再复制一张会发生漂移的职责表。

`docs/manifest.json` 的 `owns` 字段应与入口的职责地图一致。一个主题需要拆分或合并时，先重新分配权威范围，再迁移内容；不得留下两个都自称有效的定义。

发生冲突时，先核对用户当前要求与权威页，不用文件时间、篇幅、检索排名或历史评分自动判定谁更正确。需要改变设计时，修改权威页并更新引用，不能只在新页面追加一段不同说法。

维护产品语义时，以[个人助手与伙伴核心](product-requirements.md#personal-companion-core)为依据，检查新增功能如何服务主人以及是否影响原有连续性。工程底座评分、代码生成演示和项目工作台完成度不能替代核心产品验收；技术词汇中的“工程”“项目”按具体范围保留，不批量替换成产品身份。涉及核心定位的变更同时核对实施阶段、交互、记忆、架构图和验收的入链。

<a id="book-organization"></a>
### 全书章节树与技术文档归类

所有当前与后续技术文档统一纳入“篇 → 章 → 节 → 小节”体系。篇按产品或工程领域分组，章对应一个有明确职责的主题文件，章内使用 H2 节、H3 小节，复杂小节可细分 H4；不能跳过标题层级。每篇正文只保留一个 H1 文档标题，H2—H4 必须有独立的显式稳定锚点。

章节在全书中只有一个主归属；跨领域内容用链接关联。例如，记忆的数据语义归知识章，组件对比归技术栈章，同步协议归共同体章，模型选择归模型章，验收归验证章。其他章节以摘要链接到权威位置，不能为了“放在一起”复制多份完整方案。总目录与各章导航将它们组织成可连续阅读的整本设计。

机器可读的篇/章归属与顺序只维护于 `docs/manifest.json` 的 `book.parts`，其中 `chapters` 引用已有文档 ID；文档标题与职责仍在 `documents` 登记。正文标题和锚点是节/小节的唯一来源。显示的章节序号可随编排更新，不能用它替代稳定文档 ID、锚点、R/N、K/M、V、H、ADR 或 S 编号，也不能把阅读顺序解释成实施顺序。

总入口先提供清楚的阅读起点、当前进度和常用专题，再按篇展示章节表。每行显示可点击的章节名及一句“这章回答什么”，不在首页展开全部节标题；每章顶部提供完整节/小节目录，上级篇、全书目录和前后章仍可跳转。正文的知识层级不因首页简化而改变。

章节的一句话导读保存在 manifest 文档条目的 `reader_summary`，与完整职责 `owns` 分开：前者帮助读者选入口，后者界定权威范围。导读不能代替正文规则或重复维护实现状态。文件职责表、历史口径和维护命令置于首页末尾的维护者区域，不抢占首次阅读的位置。

导航由 [sync_doc_navigation.py](../tools/sync_doc_navigation.py) 生成，只维护标记块，不改正文、图源和语义。不要手工修改 `book-tree`、`book-nav`、`book-footer` 生成块；改布局应同步生成器，避免下次更新恢复旧版排版。

新增技术内容先定位已有章和节：同主题补小节；独立职责或篇幅确需拆分时，才新增已登记的章节，分配唯一主归属并修复入链。新章沿用 H1、状态/证据说明、导航标记、带稳定锚点的正文、页尾标记；不得新增游离的“补充设计”“最新方案”或未登记技术笔记作为当前权威。已替代正文迁移后清理，历史仍按现有受控历史规则处理。

每次改动章节顺序、标题或增删小节后，在仓库根目录执行：

```text
python tools/sync_doc_navigation.py --root .
python tools/check_docs.py --root .
```

导航生成器支持 `--check` 只读检查；标准文档检查已包含导航检查。检查要求每个主题页恰好归属一篇、标题与登记一致、正文层级连续、稳定锚点完整、生成目录没有过期。主题相关性、事实正确性和完整内容去向仍需编辑者审阅，不以工具通过替代。

<a id="roadmap-authority"></a>
## 3. 实施顺序与验收门分开

- K0—K6 是唯一实施顺序，由核心起步页维护。
- M0—M6 是产品能力验收门，由交付与验收页维护，不构成第二条开发时间线。
- 两者通过显式映射关联。允许先以文本和限定本地任务验证自主成长闭环，再扩展语音、界面和共同体。
- 需求优先级、开发顺序、能力验收和证据成熟度是不同维度，不得仅根据 P0、M 或章节位置推断实施先后。
- 其他页面引用阶段定义，不再维护第二张完整阶段表。

<a id="stable-identifiers"></a>
## 4. 稳定编号、锚点与清单

保留既有需求、非功能需求、K/M 阶段、验收、H 系列健康案例、ADR 和来源编号。删除或合并条目时注明被替代关系，不把旧编号重新分配给不同含义，也不为了排版连续而整体重编号。

跨页引用使用文件相对路径与显式锚点。例如，先定义 `<a id="task-unknown"></a>`，再使用 `tasks-agents.md#task-unknown`。锚点使用稳定的英文小写与连字符，不依赖标题自动生成的中文锚点。标题可以改善，已引用锚点应尽量保持；必须改变时同步全部入链。

Cursor / VS Code 用户应打开整个项目文件夹，使用内置 `Markdown: Open Preview` 阅读：Cursor 页面顶部若有 `Preview / Markdown`，先选择 `Markdown`，再按 `Ctrl+Shift+V`；内置预览的标签名为 `Preview 文件名.md`。快捷键被占用时，按 `Ctrl+Shift+P`，运行 `Markdown: Open Preview`。预览中单击链接，源码中使用 Ctrl+单击（按本机键位设置）。

项目的 [.vscode/settings.json](../.vscode/settings.json) 将预览中的 Markdown 文件链接设为 `inPreview`，继续阅读目标文档；需要直接编辑源文件时，可将该项改为 `inEditor`。这是编辑器工作区偏好，不是 Jarvis 运行配置。其他 Markdown 编辑器使用其阅读/预览模式；保持文件的相对目录关系，不要把可移植的相对路径批量改成某台电脑的盘符路径或 Cursor 专用 URI。

2026-10-15 在本机 Cursor 3.24.12 的实测：可编辑的内联 `Preview` 中点击首页链接未跳转；切换内置预览后，首页到产品需求文件、产品需求文件返回首页，以及产品需求的章内目录跳转均成功。跨文件链接中的显式锚点在本次测试中仍停在目标文件顶部，可再点击目标页的“本章导航”定位；不要把文件打开成功误记为跨页小节定位成功。其他编辑器尚未逐一实测。

链接检查通过只证明目标文件和锚点存在，不证明每种编辑器都处理相同点击动作。兼容性问题应分别验证“打开文件”和“定位小节”；第三方编辑器对显式 HTML 锚点的支持需实际确认。官方操作说明见 [VS Code Markdown 文档](https://code.visualstudio.com/docs/languages/markdown)。

`docs/manifest.json` 是有效 Markdown 的登记表。`documents` 中每项至少包含：

```json
{
  "id": "stable-document-id",
  "path": "docs/topic.md",
  "title": "文档标题",
  "owns": ["该文档独占维护的主题范围"]
}
```

`id` 与 `path` 在清单内唯一；路径相对仓库根目录。有效入口、主题页与维护文件均应登记。新增文件先确定职责，避免用文件名变化掩盖重复全文。参考文献链接必须在所在页可解析；不能假定另一个 Markdown 文件内的引用定义会自动生效。

<a id="diagram-authority"></a>
## 5. 图源与生成物

当前基线的全部 18 张图，以 `docs/diagrams/*.mmd` 为唯一可编辑图源。PNG 和 SVG 是生成物，不直接手工修改，也不在 Markdown 中保留另一份可独立编辑的 Mermaid 正文副本。

修改图时同步检查图源中的模块名、方向、权限边界、状态与主题页文字。按 [图册维护说明](architecture-atlas.md) 重新渲染，更新生成记录并检查展示结果；图可解析不等于图中系统已经实现或验证。

新增或退役图时更新图册、主题页链接、图源映射和生成记录。18 是本次基线数量，不是禁止新增图的永久上限。删除图源前确认它没有有效引用；无引用的旧生成物按明确清单清理，不扫目录猜测。

<a id="change-workflow"></a>
## 6. 一次文档变更的完成流程

1. 确定用户要求、影响范围及对应权威页；先读取必要上下文，避免重新写一套平行设计。
2. 修改权威正文。若涉及接口、权限、控制权、阶段、数据或发布机制，同步核对相邻主题。
3. 更新受影响的需求、契约、验收、ADR、来源与图源。新增、删除、移动文件时同步导航和 manifest。
4. 搜索旧文件名、旧锚点、旧编号和“第几章”等位置引用，修复失效链接和过渡说明。
5. 渲染有变化的图并检查生成物；不因只修改文案而宣称重新验证了系统运行行为。
6. 在仓库根目录运行自动检查：

```text
python tools/check_docs.py --root .
```

7. 检查失败先修复；工具不可用或仍有未解决问题时，如实记录，不能报告全部通过。最后检查改动范围，确认没有误删用户材料或留下重复有效全文。

文档检查器负责可机械核查的完整性。语义冲突、遗漏需求、错误技术结论和图文不符仍需人工或独立复核。检查器本身发生变更时，不得通过删除检查或降低标准来掩盖当前失败。

<a id="status-and-evidence"></a>
## 7. 状态与证据口径

当前总体设计状态为 `proposed`；最新局部实现和实测以[分版本证据](delivery-validation.md#versioned-evidence)为准。0.1.6 的[独立控制与恢复验收](delivery-validation.md#control-evidence)保留当时口径，不覆盖最新用户修订。0.1.5 的[运行预检验收](delivery-validation.md#preflight-evidence)、0.1.4 的[Google 模型验收](delivery-validation.md#google-models-evidence)、0.1.3 的[界面与推理级别验收](delivery-validation.md#web-workspace-evidence)、0.1.2 的[模型目录验收](delivery-validation.md#model-catalog-evidence)、0.1.1 的[聊天验收](delivery-validation.md#chat-evidence)和 0.1.0 的[种子基线](delivery-validation.md#k0-evidence)保留为历史证据。后续条目应区分：

| 状态 | 含义 |
|---|---|
| proposed | 设计建议，实施或最终冻结条件尚未满足 |
| accepted | 已按项目决定采纳，仍不表示存在运行实现 |
| implemented | 已有可定位代码或配置实现，附具体版本 |
| verified | 在明确环境与版本上通过相应验收，附证据 |

单个文件可以描述处于不同状态的模块，应逐项注明。不得因为创建目录、增加图、补充测试计划或接入外部论文，就把模块改标为 implemented 或 verified。性能目标、计划值、历史评审分数与实测结果必须分开。

未来的持续检查、自愈和自动化计划只作为设计内容；除非实际创建并确认结果，不得写成当前已经运行，也不得为维护文档擅自创建定时任务。

<a id="retirement-and-history"></a>
## 8. 退役与删除

删除旧全文或重组文件前，建立内容去向核对，保留仍有效的需求、约束、接口、案例、证据边界和历史决策理由。核对链接、图源、来源与编号后，只删除已确认被替代的具体路径。

当前有效文档树不保存旧版本全文、重复总稿或 `final-final` 类未登记副本。历史决策摘要可以留在评审页，并明确其评审对象与时间；它不恢复旧全文的权威性。

2026-10-16 主人指定 [Samuel521199/JarvisSystem](https://github.com/Samuel521199/JarvisSystem) 为项目代码仓库，授权建立本地 Git 并提交项目内容。后续以该仓库保存代码与文档历史。初次导入保留现有内容和历史证据；本机运行数据、凭据、模型、依赖缓存与可重建运行包不入库。`.gitattributes` 禁用自动换行转换，以保持图册及既有证据登记的文件摘要。发布前检查实际暂存文件，不以 `.gitignore` 代替内容检查。

删除文档副本不授权清理运行时备份、审计、未完成任务、UNKNOWN 回执、恢复材料或用户原始资料。此类对象应遵循系统自己的退役与保留设计。
